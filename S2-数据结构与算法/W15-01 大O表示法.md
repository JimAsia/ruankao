# W15-01 大 O 表示法：复杂度的定义与阶

> 复杂度不是「感觉快慢」，是一条可以被**数出来**的规则：
> **数最内层基本操作执行了多少次，取 n 趋于无穷时的量级。**
>
> 这一节把这个定义拆开，用实测数据说明每一条规则为什么成立。

---

## 一、为什么需要复杂度

同一个算法，在你的电脑上跑 1 秒，在十年前的机器上可能要 10 秒。**绝对时间不能用来比较算法。**

但「操作次数的增长趋势」是稳定的：n 从 1000 涨到 2000，次数翻倍还是变 4 倍，这个比例和机器无关。

这就是大 O：**只描述增长趋势，不描述绝对时间。**

---

## 二、定义：只保留增长最快的项

假设某段代码的操作次数是 `3n² + 5n + 100`：

| n | 3n² | 5n | 100 | 总计 | 3n² 占比 |
|---|---|---|---|---|---|
| 10 | 300 | 50 | 100 | 450 | 67% |
| 100 | 30000 | 500 | 100 | 30600 | 98% |
| 1000 | 3000000 | 5000 | 100 | 3005100 | 99.8% |

n 越大，`5n + 100` 越无关紧要，系数 `3` 也不影响「平方」这个性质。

所以都写成 **O(n²)**。

> ⭐ **三条化简规则：**
> 1. 去掉常数系数：`3n` → `n`
> 2. 去掉低阶项：`n² + n` → `n²`
> 3. 去掉常数：`n + 100` → `n`

### 实测证据：常数不影响量级

三角形循环（内层 `j < i`）和满矩阵循环（内层 `j < n`）对比：

```text
O(n^2)          = 4096 次
O(n(n+1)/2)     = 2016 次
两者比值        = 2.03
```

n = 64 时，三角形循环次数正好是满矩阵的**一半**。

> 少了一半！但复杂度**都是 O(n²)**。
> 因为 n 趋于无穷时这个比值稳定在 2 —— 常数因子，被忽略。

---

## 三、阶的排序（必须背下来）

```text
O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)
```

### 实测：n 翻倍时各阶涨多少倍

这是理解「阶」最直接的方式。用计数器实测（n=64 → 128）：

```text
O(log n)   : 7 → 8        增 1.14 倍
O(n)       : 64 → 128     增 2.00 倍
O(n log n) : 328 → 777    增 2.37 倍
O(n^2)     : 4096 → 16384 增 4.00 倍
```

| 复杂度 | n 翻倍时 | 记忆点 |
|---|---|---|
| O(1) | 不变 | 和 n 无关 |
| O(log n) | **只 +1** | 减半类 |
| O(n) | ×2 | 线性 |
| O(n log n) | ×2 多一点 | 排序类 |
| O(n²) | ×4 | 双层循环 |
| O(n³) | ×8 | 三层循环 |
| O(2ⁿ) | **平方** | 指数爆炸 |

> ⭐ 这张表就是复杂度的定义。考试里问「哪个增长最快」，比的就是这张表。

---

## 四、完整对照：各种阶的实际数字

实测（`151_bigO.c`）：

```text
n          O(log n)     O(n)       O(n log n)     O(n^2)
8          4            8          21             64
16         5            16         54             256
32         6            32         135            1024
64         7            64         328            4096
128        8            128        777            16384
```

注意 `O(log n)` 这一列：n 从 8 涨到 128（涨 16 倍），它只从 4 涨到 8（只多了 4）。

> ⭐ 这就是为什么二分查找、平衡树这么强 —— **数据量翻 16 倍，工作量只多 4 次**。

## 五、时间与理论要能对上

数出来的次数是理论，`clock()` 量的是实测。两者必须一致，复杂度才可信。

实测（`152_growth.c`，本机 CPU）：

```text
=== O(n)：n 翻倍，时间应该翻倍 ===
  n          耗时(ms)   比上一行
  33554432   6.000
  67108864   13.000       2.17 倍
  134217728  26.000       2.00 倍
  268435456  53.000       2.04 倍

=== O(n^2)：n 翻倍，时间应该变 4 倍 ===
  n          耗时(ms)   比上一行
  4000       3.000
  8000       14.000       4.67 倍
  16000      57.000       4.07 倍
  32000      228.000      4.00 倍
```

**2.0 倍 vs 4.0 倍** —— 这就是复杂度的真实含义：它预测「规模变大时会发生什么」。

### 但计时不能用来「得出」复杂度

三个陷阱：

1. **受机器影响**：同一段代码，换台机器差 5 倍
2. **受常数影响**：O(n) 但循环体极重，可能比 O(n²) 循环体极轻还慢
3. **小数据看不出**：n=10 时，O(n²) 和 O(n log n) 都不到 1 微秒，全量出 0

> ⚠️ 我在实测时就踩了第 3 个坑：一开始 O(n) 用 n = 100 万，`clock()` 精度只有 1 毫秒，全部输出 `0.000`。必须把 n 放大到 3000 万以上才量得出来。
>
> **这就是为什么复杂度分析要「数次数」，而不是「掐表」。**

## 六、最好、最坏、平均复杂度

同一个算法，不同输入的次数可能差很多。以顺序查找为例：

| 情况 | 查找位置 | 比较次数 | 复杂度 |
|---|---|---|---|
| 最好 | 第一个元素 | 1 | O(1) |
| 最坏 | 最后一个 / 不存在 | n | O(n) |
| 平均 | 随机位置 | n/2 | O(n) |

**默认说「复杂度」指的是最坏情况**，因为它给出性能保证。

> 📌 软考题里如果问「平均时间复杂度」，要单独看。比如**快速排序**：
> 平均 O(n log n)，最坏 O(n²)（数据已有序且取首元素为基准时）。
> 这个「最坏退化」是高频考点。

## 七、指数级：为什么它可怕

实测朴素斐波那契的调用次数：

```text
n      O(2^n) 次数  对比 O(n^2)
5      15             25
10     177            100
15     1973           225
20     21891          400
25     242785         625
30     2692537        900
```

n = 30 时，指数级已经 **269 万次**，平方级只有 **900 次**。

### 换算成时间（每秒 1 亿次操作）

| 复杂度 | n = 10⁶ 时 | 现实感受 |
|---|---|---|
| O(log n) | 约 20 次 | 瞬间 |
| O(n) | 100 万次 | 0.01 秒 |
| O(n log n) | 2000 万次 | 0.2 秒 |
| O(n²) | 1 万亿次 | **约 2.8 小时** |
| O(2ⁿ) | 天文数字 | 宇宙毁灭也算不完 |

> ⭐ **这就是「把 O(n²) 优化成 O(n log n)」价值巨大的原因**：
> 100 万条数据，前者几小时，后者零点几秒。

## 八、软考怎么考

| 考点 | 典型问法 | 要点 |
|---|---|---|
| 化简 | `3n²+5n+100` 的复杂度 | O(n²)，去系数去低阶 |
| 排序 | 哪个增长最快 | 背那张阶的顺序表 |
| 判断循环 | 给代码问复杂度 | 数循环层数与步长 |
| 最坏/平均 | 快排的最坏情况 | O(n²) |
| 实际换算 | n=10⁶ 用 O(n²) 要多久 | 数量级估算 |

> 📌 **复杂度是 S2 的地基。** 后面学链表、树、排序、查找，每个都要标复杂度。
> 这一周没搞懂，后面每一节都会觉得虚。
